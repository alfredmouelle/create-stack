# Adding a framework

This guide is for the owner of a new framework module, such as Remix or RasenganJS.
It names the files you create, the two shared lines you add, and the checks your
framework must pass. Read [CONTEXT.md](../CONTEXT.md) for the vocabulary and
[ADR-0002](./adr/0002-assemble-projects-from-framework-modules.md) and
[ADR-0003](./adr/0003-engine-owned-quality-profile.md) for the reasons behind the model.

## What you create and what you leave alone

Replace `<id>` with your canonical framework id, for example `remix`.

| You create | Purpose |
| --- | --- |
| `cli/src/frameworks/<id>.ts` | The framework module: the entry point the registry imports. |
| `cli/src/frameworks/<id>-parts.ts` | The reference application's parts. |
| `cli/src/frameworks/<id>-renderers.ts` | Renderers for files that depend on several parts, when you have any. |
| `cli/src/frameworks/<id>-additions.ts` | Capability, mailer, and component wiring for `create-stack add`. |
| `apps/<id>-base/` | The reference application. The pnpm workspace already includes `apps/*`. |
| `cli/templates/<id>/` | Variant files: part files that differ from the reference application's recommended form. |

You add exactly two shared entries:

1. In `packages/stack-config/src/index.ts`, add `<id>` to `FRAMEWORKS` and add its
   `FRAMEWORK_SUPPORT` entry (see [Framework support](#framework-support)).
2. In `cli/src/framework-registry.ts`, import your module and add it to `frameworkModules`.
   `cli/scripts/list-frameworks.ts` prints this list for the CI smoke matrix.

Everything else is shared and stays unchanged in your framework change: the engine
(`cli/src/engine.ts`), the contract (`cli/src/framework-module.ts`), the quality profile
(`cli/src/quality-profile.ts`), the assembly toolkit (`cli/src/reference-application.ts`,
`cli/src/javascript/`), the CLI (`cli/index.mjs`, `cli/engine.mjs`, `cli/src/commands/`, `cli/src/lib/`), packaging
(`cli/scripts/bundle.ts`), CI workflows, the marketing configurator behavior, and the conformance
test infrastructure in `cli/test/`. Complete the framework details/tree data and explicit test fixtures when adding a registered framework. The shared template directories (`cli/templates/database/`,
`testing/`, `javascript/`, `quality-profile/`) and the shared JavaScript parts in
`cli/src/javascript/reference-parts.ts` belong to the toolkit too. Help, prompts, the creation plan, `add` detection, bundling, the CI
smoke matrix, and core configurator choices derive from the two entries above. Marketing framework details/tree data and framework-specific test fixtures also require explicit entries. When the
toolkit lacks something you need, propose it as its own change first.

`cli/test/framework-boundaries.test.ts` fails when your framework id appears in shared CLI
code, so framework knowledge stays inside `cli/src/frameworks/`.

## The framework module

A module is a `FrameworkModule` value (`cli/src/framework-module.ts`). TypeScript
reports a missing or mistyped field as you write it. `cli/src/frameworks/next.ts` and
`cli/src/frameworks/tanstack.ts` are complete examples.

| Field | Responsibility |
| --- | --- |
| `id` | The canonical id declared in `FRAMEWORKS`. |
| `label`, `maturity` | Your identity, read from your `FRAMEWORK_SUPPORT` entry rather than repeated. |
| `detect(applicationDir)` | Return `true` for an application of your framework, including projects generated by earlier Create Stack versions. `add` uses the first registered module that matches, so detection must reject every other registered framework, including frameworks that share your dependencies. |
| `assemble(request)` | Write the project for a resolved configuration into `request.projectDir` and return the application directory and any manual steps. The contract does not mandate a strategy; the existing modules use `assembleProject` from `cli/src/javascript/project-assembly.ts`. |
| `additions` | `componentRoot` (the file where callable components mount, or `null` when components are unsupported) and one `CapabilityAddition` per supported capability, listing its providers. `add` rejects anything absent here before it changes a file. JavaScript frameworks build this with `javascriptAdditions`. |
| `gate(packageManager)` | The install, format, typecheck, and lint commands of the [verification gate](#verification-gate). |
| `monorepoOutputs` | Build outputs and caches for Turborepo and Nx, read from your `FRAMEWORK_SUPPORT` entry rather than repeated. |
| `packagedAssets` | Repository paths copied into the published CLI, normally `['apps/<id>-base']`. |
| `assetExcludes` | Generated file names left out of the package, such as `next-env.d.ts`. |
| `qualityProfileExceptions` | Declared [quality profile exceptions](#quality-profile-exceptions), normally `[]`. |
| `applyQualityProfile(request)` | Write the quality profile into your toolchain's files: the profile options, hook preparation, and the selected formatter and linter. The engine copies the shared hooks and editor settings first and never reads your manifests. JavaScript frameworks use `applyJavaScriptQualityProfile`. |
| `referenceApplication` | The parts declaration. Setting it enrolls your framework in the reference conformance suite. |

## Framework support

`FRAMEWORK_SUPPORT[<id>]` in `packages/stack-config/src/index.ts` declares, once:

- `label`: the name shown in help, prompts, the plan, and the configurator.
- `maturity`: `stable`, or `preview` while the framework depends on prerelease upstream
  packages.
- `monorepoOutputs`: build outputs and caches for Turborepo and Nx, for example
  `['.next/**', '!.next/cache/**']`. The website shows the same list, and your reference
  application's `turbo.json` declares it as its `build` outputs (own that file with
  `source: null`).
- `supports`: the values your framework implements for each stack axis (`database`,
  `auth`, `trpc`, `mailer`, `formatter`, `linter`).
- `recommendations`: the values applied to axes the user leaves unchosen. They must be
  supported values.

The resolver reports an explicit choice outside `supports` as a choice conflict before
any file is written; it never substitutes another value. Declare only what your
reference application implements: the conformance suite assembles every supported
database, auth, tRPC, and mailer combination, and the quality tool tests run every
formatter and linter combination.

## Reference application and part ownership

`apps/<id>-base` is a runnable, tested application containing every stack part your
framework supports, in its recommended form. Generation copies the selected parts of it
and never deletes files.

Declare a `ReferenceApplication` (`cli/src/reference-application.ts`): the application
root and its parts. A part has an `id` (`skeleton`, `auth:clerk`, `database:prisma`,
`trpc`, a mailer provider, `testing`), a `selected(selection)` predicate, its files, and
its data: dependencies, scripts, and environment keys. Each part file takes one of four
forms:

- **Copied**: `source` is the reference file's path and `referencePath` names it.
- **Rendered**: `source` is a function of the selection and the selected parts. Use it
  only for files that depend on several parts, such as the application root, providers,
  the environment schema, and `package.json`.
- **Variant**: `source` points into `cli/templates/<id>/` and has no `referencePath`. Use
  it for an alternative that differs from the recommended form, such as Prisma when
  Drizzle is recommended.
- **Generated elsewhere**: `source: null` with a `referencePath`, for a tracked file that
  another step writes, such as `.gitignore` or a router's generated route tree.

The rules the conformance suite enforces:

- Every Git-tracked file of `apps/<id>-base` has exactly one owning part through
  `referencePath`.
- Two selected parts never write the same path.
- Each rendered file, for the recommended configuration, equals the reference
  application's file byte for byte.
- No generated file imports a package or module that the selected parts do not provide.

`cli/src/javascript/reference-parts.ts` supplies the shared JavaScript parts: the
skeleton (which renders `package.json` and `src/env.ts`), the SQL database parts, the
mailer parts, and the testing part.

## Verification gate

Before the automatic first commit, the engine runs `install`, then `format` (with fixes),
`typecheck`, and `lint`, all required to pass. Your module supplies each command; the
engine assumes no `package.json` script. JavaScript frameworks use `packageScriptGate`,
which runs the generated project's `check:write`, `typecheck`, and `check` scripts. The
selected quality tools write `check:write` and `check`; your reference application owns
`typecheck`, including any code generation it needs. Tests and builds stay outside the
gate.

## Quality profile exceptions

After assembly, the engine applies the quality profile to the generated application:
the strict TypeScript options in `QUALITY_PROFILE_OPTIONS`, Git hooks for the selected
tools, hook preparation, and editor settings. Your reference application's
`tsconfig.json` enables every profile option itself and adds only framework options
(JSX, paths, plugins, types). Generation fails when a generated `tsconfig.json` sets a
profile option, or a member of `strict`, to `false`.

A framework without shadcn can pass `tailwindStylesheet` to
`applyJavaScriptQualityProfile` in its `applyQualityProfile` implementation. The path
is relative to `applicationDir`; the toolkit resolves it from the project-level
Prettier configuration, including in monorepos. When omitted, the toolkit reads
`tailwind.css` from the application's `components.json` as before.

When an upstream framework forces a relaxation, declare it:

```ts
qualityProfileExceptions: [
  { option: 'verbatimModuleSyntax', reason: 'The <framework> compiler rewrites type-only imports' },
],
```

Each exception names a profile option and a non-empty reason, and the quality profile
tests cover it. Correct reference code at the source rather than with casts or
exceptions.

## Packaging

`cli/scripts/bundle.ts` copies every `packagedAssets` path of every registered module into
the published package. It leaves out `node_modules`, `dist`, `.turbo`, `start-database.sh`,
`.env` files, `*.tsbuildinfo`, your `assetExcludes`, and the first path segment of each
`monorepoOutputs` entry that does not start with `!`. At runtime, the
module reads its reference application through `STACK_ROOT` (`cli/src/lib/paths.ts`), which
resolves to the bundle when the CLI is packed and to the repository otherwise. Read
reference files through `STACK_ROOT` and variant files through `TEMPLATES`, never through
paths relative to your module.

## Conformance obligations

Once your module is registered, these suites run against it without changes:

| Suite | Your framework must |
| --- | --- |
| `framework-registry.test.ts` | match `FRAMEWORKS` one to one, appear in the `list-frameworks.ts` output, and supply every gate command. The test currently expects the `packageScriptGate` commands. |
| `framework-boundaries.test.ts` | keep its id out of shared CLI code. |
| `framework-conformance.test.ts` | satisfy the part ownership rules above for every supported combination when generated through the engine, detect its own generated projects, and assemble a minimal project without deleting existing files. |
| `quality-profile.test.ts` | ship a reference `tsconfig.json` with the full profile, apply the profile, hooks, and editor settings in standalone, Turborepo, and Nx projects, and give every exception a reason. |
| `quality-tools*.test.ts` | pass every formatter and linter combination on the reference application, in every monorepo shape, with tool configurations at the correct level. |
| `package-content.test.ts` | ship its packaged assets, including `package.json` and `src/lib/site-config.ts`, without generated or excluded files. |

Tool conformance runs in separate standalone, Turborepo, and Nx test files so Vitest
can schedule each project shape independently. Each file iterates the framework registry.
The CLI suite caps workers at four locally and two in CI to bound concurrent compiler
and linter subprocesses on hosted runners.

Cover what only your framework does, such as detection fixtures and its component
root, in your own `cli/test/<id>.test.ts`. The smoke and packed certification
suites build real projects; run them before you mark your framework `stable`. They hold
framework-specific expectations keyed by id: add your entry to `SHADCN_CONFIGURATIONS`
in `cli/test/smoke.test.ts` and your themed surface to `cli/test/branded-surface.ts`.
